TÍTULO / GANCHO:
Monitoramento vs Observabilidade: pare de confundir

LEGENDA COMPLETA (cole isso no Business Suite):
----------------------------------------------------------------------
Monitoramento clássico: "o servidor tá UP?" (Nagios, Zabbix)
Observabilidade moderna: "por que o request do user X levou 5s no endpoint Y?"

Os 3 pilares que você PRECISA dominar:

🔢 Métricas (Prometheus)
Números ao longo do tempo: latência, CPU, requests/s

📝 Logs (Loki)
Eventos textuais: "error no handler X", "query lenta"

🔍 Traces (Jaeger/Tempo)
Jornada de 1 request através de N microsserviços

Exemplo real de investigação:
User reporta: "tá lento"
→ METRICAS: P99 latência subiu de 200ms pra 3s às 14:32
→ LOGS: às 14:32 apareceu "slow query: SELECT * FROM costs WHERE..." (2.8s)
→ TRACES: Request ID abc123 passou 2.8s em "DB Query"
→ Causa raiz: full table scan por falta de índice

TÍTULO / GANCHO:
3 estratégias de isolamento em SaaS Multi-Tenant (prós/contras)

LEGENDA COMPLETA (cole isso no Business Suite):
----------------------------------------------------------------------
Você quer transformar seu projeto em SaaS. Primeira decisão técnica:
COMO separar os dados dos clientes?

1️⃣ Database per Tenant
✅ Isolamento máximo (compliance, enterprise)
❌ Custo altíssimo (N databases)
❌ Migrations em N bancos

2️⃣ Schema per Tenant
✅ Isolamento bom, mesmo database
✅ Backup por tenant
❌ Schemas multiplicando
❌ Conexões Prisma complicadas

3️⃣ Row-Level Isolation (clientId em toda tabela)
✅ MELHOR CUSTO
✅ Escala pra milhões de tenants
❌ Requer disciplina (middleware obrigatório)
⚠️ Risco #1 da indústria: data leak entre tenants

👉 90% dos SaaS do mercado usam opção 3 (inclusive o Slack, Notion, Figma).

No Ebook 3 da Trilha eu mostro como implementar Row-Level Isolation em Prisma com middleware que INJETA o clientId automaticamente — impossível esquecer e vazar dados.

TÍTULO / GANCHO:
SLO, SLI e Error Budget: a matemática da confiabilidade

LEGENDA COMPLETA (cole isso no Business Suite):
----------------------------------------------------------------------
Se você vai trabalhar com SRE, esses 3 conceitos mudam tudo:

📊 SLI (Service Level Indicator)
Métrica que MEDE confiabilidade.
Ex: "% requests com status < 500"

🎯 SLO (Service Level Objective)
META para o SLI.
Ex: "99.9% dos requests em < 200ms"

💰 Error Budget
Quanto PODE falhar sem violar o SLO.

Tabela de uptime realista:
99% → 7.3 horas de downtime/mês (Generoso)
99.9% → 43 min (Moderado) ← seu primeiro alvo
99.95% → 21 min (Apertado)
99.99% → 4 min (Muito raro)
99.999% → 26 seg (Quase impossível)

📌 Regra: não existe "100% de uptime". Alvos irreais queimam o time.

📌 Regra: Error Budget esgotou? FEATURE FREEZE. Foca só em reliability até restaurar.

TÍTULO / GANCHO:
Reduzi imagem Docker de 1.2GB pra 150MB (mesmo código)

LEGENDA COMPLETA (cole isso no Business Suite):
----------------------------------------------------------------------
Segredo: multi-stage build.

ANTES (errado):
FROM node:20
COPY . .
RUN npm install
RUN npm run build
CMD ["node", "dist/index.js"]
→ 1.2 GB (inclui source, node_modules dev, docs, etc)

DEPOIS (correto):
FROM node:20-alpine AS builder
COPY . .
RUN npm ci
RUN npm run build

FROM node:20-alpine AS production
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
CMD ["node", "dist/index.js"]
→ 150 MB (só o necessário pra rodar)

Benefício real:
→ Deploy 8x mais rápido
→ Imagem registry 8x mais barato
→ Superfície de ataque 80% menor
→ Pull no K8s mais rápido = escala mais rápida

└─ users, credentials (encrypted AES-256-GCM), costs, alerts, ai_history

Por que Adapter Pattern?
Cada cloud tem API diferente. Adapter normaliza num schema comum.

Por que credenciais encriptadas?
AES-256-GCM no DB + chave em env. Se vazar o DB, credencial não vaza.

Por que Prisma?
Middleware injeta clientId automaticamente (Row-Level Isolation).
